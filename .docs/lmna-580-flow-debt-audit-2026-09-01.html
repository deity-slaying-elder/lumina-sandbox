Why they hit limits

Root cause

Eleven of the twelve after-save Flows on Patient__c update $Record — the record that just triggered them. Each of those is a separate DML statement that starts a fresh save order, which re-evaluates all twelve Flows again.

Nothing upstream needs to be pathological for this to blow up. One Admission/Discharge insert issues six Patient updates before any Patient Flow has run.

Same-record after-save updates Primary cause

All eleven are plain field assignments on the triggering record — name concatenation, consent timestamps, status derivation, a 48-hour counter. This is before-save work being done after-save. Before-save costs zero DML; after-save costs one DML plus a full re-entry, each time.

Patient ↔ Community Episode write cycle Cycle

Patient_TF_On_Update_Last_SMS_Update_Latest_Episode writes Last_SMS_Sent_Date__c onto Community Episode. Community_TF_On_Update_Status_Call_Outcome_Update_Patient queries the Patient and writes back. Each pass consumes save-order depth against the 16-deep recursion cap.

Heavy multi-update flows Amplifier

Opportunity_TF_On_Closed_Won_Update_Facility_Program holds 9 record updates, Facility_TF_On_Update_Rollout_Status_Capture_User holds 6, and Admission_Discharge_TF_On_Create_Set_Latest_A_D_on_Patient holds 5 — all separate DML statements that a single Apex update would collapse into one.

Loops are clean Not a problem

Worth stating because it is the usual suspect: no flow in the org performs DML or a query inside a loop. Facility_Mapper_TF_Delete_False_Leaked_Admissions collects into a variable and deletes once after the loop. The loops are correctly bulkified — leave them alone.

Delete before you convert

Quick wins

Three redundancies found. The first is free — two flows are functionally identical, so one is pure overhead and one fewer conversion.

Exact duplicate Deactivate one

Patient_TF_On_Update_Update_Name and Patient_TF_On_Update_of_First_or_Last_Name_Update_Name have identical entry criteria (First_Name__c or Last_Name__c IsChanged) and identical bodies (set $Record.Name). One is dead weight.

Contending consent writers Consolidate

Patient_TF_On_Update_Of_Consent_Set_DateTime and Patient_TF_On_update_of_consent_status_update_consent_datetime both write Consent_Datetime__c on $Record under different, overlapping conditions. Which one wins depends on flow order — which is not guaranteed. Needs a decision on the intended rule before either is ported.

Unfiltered pair on Payer Verification Consolidate

Patient_Verification_TF_On_Create_Update_Patient and Payer_Verification_TF_On_Create_Update_Patient both fire on every Payer Verification insert with no entry criteria at all, and both update the related Patient. Three Patient DMLs per insert where one would do.

Conversion sequence

Plan

Ordered by risk-adjusted payoff, not by object. Phases 1–3 remove most of the limit pressure without writing much Apex; the bulk conversion only makes sense once the cascade is flattened.

1

Sync and baseline

Land the 24 missing flows in source control and reconcile the 14 stale repo flows. Nothing else is reviewable until the repo matches the org.

Exit: sf project retrieve start produces an empty diff for Flow metadata.

2

Delete the duplicate, decide the two overlaps

Deactivate the redundant name flow outright. For the consent pair and the Payer Verification pair, get the intended business rule from Chana before porting — encoding an ambiguity into Apex just makes it harder to see.

Exit: 3 flows deactivated, 2 rules written down. Needs: Chana.

3

Collapse the Patient self-updates into one before-save handler

The single highest-value change. Extend the existing PatientTrigger to before insert, before update coverage and fold the eight remaining $Record-only flows into PatientTriggerHandler alongside setLocalAppointmentTimes. Field assignment in a before-trigger costs no DML and no re-entry.

  • Name concatenation, consent datetime, community status datetime
  • Discharge community status, program eligibility, 48-hour call count
  • Closed-won state check, discharge-home IC assignment

Exit: Patient after-save flow count 12 → 2. Est. DML per Patient save drops by an order of magnitude.

4

Break the Community Episode cycle

Both directions are one-field writes. Move them into a single Apex service invoked from whichever side actually owns the data, so the round trip becomes one pass instead of a ping-pong. This is the piece that most needs a decision rather than code — which object is the source of truth for episode SMS state.

Exit: no bidirectional writes between the two objects. Needs: a data-ownership call.

5

Port the TCM cross-object flows

Now the actual ticket text. With Patient flattened, these become straightforward handler classes following the existing PatientTriggerHandler / OpportunityTriggerHandler pattern — one trigger per object, logic in the handler, tests alongside.

  • Admission_Discharge__c — 3 flows, incl. the 5-update Patient setter and the SMS send
  • Hospital_Admission__c — prior NH discharge lookup
  • Visit__c — 4 Patient updates collapse to 1
  • Community_Episode__c — 4 flows, 2 already before-save

Exit: TCM path is Apex end to end, flows deactivated not deleted, 75%+ coverage.

6

Everything else, by weight

Remaining 20-odd flows. Take Opportunity_TF_On_Closed_Won_Update_Facility_Program (9 updates) and Facility_TF_On_Update_Rollout_Status_Capture_User (6) first; the single-update name formatters last, and only if there is a reason beyond consistency.

Open question: is the goal zero flows, or zero fragile flows? A one-element name formatter is not costing anything.
